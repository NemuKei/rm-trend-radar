# DECISIONS

## D-20260502-001: 新規 private repo として開始する

- 決定日: 2026-05-02
- 決定: `market-stats-viewer` へ統合せず、`rm-trend-radar` という新規プロジェクトとして開始する。
- 理由: `market-stats-viewer` は会場公式データの取得と表示を主対象にしている。一方でこのプロジェクトは、ホテル・レベニューマネジメント領域の記事リンク、要約、タグ、重要度、示唆を扱う。入力データ、著作権上の注意点、画面設計、将来の公開範囲が異なるため、同じリポジトリへ入れると責務が混在する。

## D-20260502-002: MVP は Python、Streamlit、SQLite とする

- 決定日: 2026-05-02
- 決定: 初期 MVP は Python、Streamlit、SQLite のローカル構成で開始する。
- 理由: 個人利用で記事確認体験とデータ構造を検証する段階では、公開基盤、認証、クラウド DB を先に導入するより、ローカルで短い周期で変更できる構成のほうが適している。

## D-20260502-003: Cloudflare と独自ドメインは初期 MVP に含めない

- 決定日: 2026-05-02
- 決定: Cloudflare と独自ドメインは、初期 MVP ではアプリ本体の前提にしない。
- 理由: 公開化すると、認証、原文リンクと要約の公開範囲、定期実行、取得頻度、DB 配置を同時に判断する必要がある。まずは private repo のローカルアプリとして、扱うデータと確認体験を確定する。

## D-20260502-004: 取得対象調査と取得契約は `spec_001_sources.md` に分離する

- 決定日: 2026-05-02
- 決定: 公開 RSS、公開ブログ一覧ページ、取得頻度、保存項目、取得停止条件は `docs/spec_001_sources.md` を正本にする。
- 理由: 取得対象サイトの判断は、アプリ全体の概要よりも独立した外部契約を持つ。今後、対象サイトの追加、取得頻度の変更、取得方法の変更が複数回発生する見込みがあるため、`docs/spec_000_overview.md` に混在させず、専用仕様として管理する。

## D-20260502-005: 初期 MVP の取得対象は RSS が確認できる 5 件に絞る

- 決定日: 2026-05-02
- 決定: 初期 MVP の記事取得対象は、IDeaS、SiteMinder、RoomPriceGenie、Revfine、Hotel Speak の 5 件にする。
- 理由: 5 件はいずれも公式 RSS またはカテゴリ別 RSS が確認でき、robots.txt で RSS またはブログ記事への一般取得が明示的に禁止されていない。Mews は robots.txt で `*/feed` が禁止されている。Lighthouse は RSS が確認できず、公開ブログ一覧ページの解析が必要である。Hospitality Net は公式 RSS と `/rss/` の robots.txt Allow が確認できるが、ニュース範囲が広く、初期 MVP で扱う対象を広げすぎるため後回しにする。

## D-20260502-006: 初期 MVP では AI API を使わず手動確認済みデータを蓄積する

- 決定日: 2026-05-02
- 決定: 初期 MVP では、AI 要約、AI タグ付け、AI 重要度付け、AI 示唆生成を実装しない。先に、取得済み記事を人間が確認し、日本語要約、タグ、重要度、レベニューマネジメント担当者向けの示唆、手動メモ、確認状態を保存できるようにする。週次ダイジェストは、確認済み記事の保存済みデータから Markdown を機械的に組み立てる。
- 理由: 現在保存している RSS 項目は、記事 URL、取得元、公開日、英語タイトル、RSS category を中心にしたメタデータである。記事本文と RSS `description` は保存していない。この状態で AI に要約や示唆を生成させると、原文内容に基づかない推測が混ざる可能性がある。まずは人間が確認したデータを蓄積し、AI に渡す入力データ、保存してよい出力、保存しないデータの扱いを後続で判断できる状態にする。

## D-20260502-007: 収集確認リポジトリと公開 LP の責務を分ける

- 決定日: 2026-05-02
- 決定: `rm-trend-radar` は、記事データ、AI 要約候補、タグ、重要度、示唆、手動メモ、公開候補フラグを持つ非公開の収集確認リポジトリとして扱う。副業リポ側 LP は、公開してよい記事だけを材料に、原文記事の代替にならない短い紹介、独自の見解、業務上の示唆を掲載する公開面として扱う。
- 理由: 収集確認段階では未確認記事、AI 候補、手動メモ、原文確認前の仮要約が混在する。これを公開 LP と同じ場所で扱うと、未確認情報の公開、原文代替に近い転載、公開範囲の誤りが起きやすい。非公開の管理面で選別し、公開面には確認済みで公開してよい内容だけを渡す構成にする。

## D-20260503-008: 公開 LP と X は短い導線に留め、詳細理解は原文サイトに戻す

- 決定日: 2026-05-03
- 決定: 副業リポ側 LP と X では、確認済み記事の短い紹介、独自の示唆、原文リンクを掲載する。詳細な内容理解は、利用者が原文サイトを開いて確認する前提にする。ブラウザの翻訳機能を使えば、日本語化された全文の確認は原文サイト側で行えるため、`rm-trend-radar` や公開 LP は原文記事の代替になる長文を持たない。
- 理由: 原文サイトへの送客と著作権上の安全性を優先するため。公開面で長い要約や本文代替に近い説明を持つと、原文記事を読まなくても内容が分かる状態に近づく。公開 LP と X は発見と導線の役割に限定し、詳細確認は原文サイトで行う方針にする。

## D-20260504-009: 副業リポ側 LP の初期掲載はタイトル、短い要約、原文リンクの一覧に限定する

- 決定日: 2026-05-04
- 決定: 副業リポ側 LP の初期実装では、公開候補記事を一覧として掲載する。記事ごとに日本語タイトル、短い要約、取得元、公開日、原文リンクだけを表示する。`public_tip_ja` の長い日本施設向け解説、SNS 投稿案、メルマガ用リード文、社内共有用 3 行要約、支配人・現場向けチェックリストは初期一覧には表示しない。
- 理由: 最初から長い個別解説ページを作ると、公開ページが原文記事の代替に近づきやすい。まずは記事発見と原文サイトへの導線に限定し、どの記事を外部向けに紹介する価値があるかを確認しやすくする。長い独自解説は、掲載価値が確認できた記事だけを別タスクで扱う。

## D-20260504-010: 副業リポ側 LP に初期取得対象 5 サイトの紹介を載せる

- 決定日: 2026-05-04
- 決定: 副業リポ側 LP には、海外記事一覧と合わせて、初期取得対象である `IDeaS`, `SiteMinder`, `RoomPriceGenie`, `Revfine`, `Hotel Speak` の短い紹介を掲載する。紹介文は、各サイトの公式説明文の転載ではなく、このプロジェクトで確認する情報源としての役割を説明する。
- 理由: 記事一覧だけを出すと、読者が情報源の性格を判断しづらい。各サイトが主に扱うテーマを短く示すことで、海外記事一覧の意図と参照範囲を理解しやすくする。一方で、初期取得対象ではない `Mews`, `Lighthouse`, `Hospitality Net` は、まだこの LP の参照元として扱わない。

## D-20260504-011: 次段階の自動化は記事取得だけに限定する

- 決定日: 2026-05-04
- 決定: 初期 MVP の次段階では、RSS の定期取得を追加してよい。ただし、自動化する範囲は記事メタデータの取得と SQLite への upsert までに限定する。日本語化、重要度確定、公開候補フラグ付け、副業リポ側 LP への反映、X 投稿は自動化しない。
- 理由: 新着記事の取りこぼしを減らす効果は、記事取得だけでも得られる。一方で、日本語化や公開 LP 反映まで自動化すると、原文確認前の情報、原文記事の代替に近い長文、内部メモ、公開してよいか未判断の内容が外部に出るリスクが増える。掲載判断を人間の確認ワークフローに残すことで、公開範囲と著作権上の制約を維持しながら運用負荷を下げる。
- 後続決定: 2026-05-11 の `D-20260511-014` で、短い記事一覧データに限定する条件付きで、副業リポ側 LP 反映まで自動化してよい方針へ改定した。

## D-20260504-012: 定期取得の主経路は GitHub Actions にする

- 決定日: 2026-05-04
- 決定: 定期取得の主経路は GitHub Actions にする。GitHub Actions では、RSS のメタデータだけを取得し、`rss_snapshot.json` を artifact として保存する。GitHub Actions からローカル SQLite、公開候補フラグ、副業リポ側 LP のファイルは更新しない。
- 理由: Windows タスクスケジューラは PC が起動している場合にだけ実行されるため、記事取得の取りこぼしを減らす用途ではクラウド実行のほうが安定する。一方で、GitHub Actions から公開 LP まで自動反映すると、未確認記事が公開面へ出る危険がある。したがって、クラウド側では取得結果の確認材料だけを残し、掲載判断は `rm-trend-radar` の人間確認ワークフローに残す。
- 後続決定: 2026-05-11 の `D-20260511-014` で、GitHub Actions の頻度を 3 日に 1 回程度へ変更し、副業リポ側 LP の短い記事一覧データ更新までを自動化してよい方針へ改定した。

## D-20260504-013: 公開 LP 用カテゴリは RTR 側の確認項目として保存する

- 決定日: 2026-05-04
- 決定: 公開 LP 用の単一カテゴリを `public_category` として `rm-trend-radar` 側に保存する。値は公開 LP の初期 6 カテゴリに対応する slug とし、記事確認画面または確認済みレビュー画面で人間が選択する。公開候補 export には `public_category` と表示ラベルを含める。
- 理由: 公開 LP 側で記事を再分類すると、記事内容を確認した作業の判断が LP 実装側へ移り、更新時の思考コストと分類ぶれが増える。RTR 側で公開候補を決める段階でカテゴリまで確定すれば、公開 LP 側は export の値を使ってカテゴリ別表示を生成できる。

## D-20260511-014: 最新記事取得と副業リポ側 LP 反映は 3 日に 1 回程度で自動化する

- 決定日: 2026-05-11
- 決定: `D-20260504-011` と `D-20260504-012` の「副業リポ側 LP への反映は自動化しない」という部分を改める。今後は、最新記事の取得から副業リポ側 LP の記事一覧データ更新までを自動化してよい。ただし役割は分ける。GitHub Actions は RSS メタデータ取得だけを担当し、翻訳、短い紹介文作成、公開候補化、副業リポ側 LP 反映、検証レポートは Codex アプリの automation が担当する。
- 実行頻度: GitHub Actions の RSS snapshot は 3 日に 1 回程度、14:37 JST 相当で実行する。Codex アプリ automation は、GitHub Actions の取得後に少し時間を置くため、3 日に 1 回程度、15:10 JST に実行する。
- Codex automation: automation ID は `rm-trend-radar-lp-reflection` とする。対象 workspace は `C:\Users\n-kei\dev\github\rm-trend-radar` と `C:\Users\n-kei\dev\SideBiz_HotelRM` である。
- 自動化してよい処理: RSS snapshot またはローカル DB の取得済みメタデータを確認する。LP 用の短い日本語タイトル、原文記事の代替にならない短い紹介、公開カテゴリを生成または更新する。副業リポ側 LP が参照する記事一覧データを更新する。必要な検証を実行し、結果、差分、保留記事を報告する。
- Codex automation は、検証が通過した場合、変更がある repository ごとに commit し、現在の追跡先 branch へ push する。検証失敗、公開対象外項目の混入、原文記事の代替になる長文、判断に迷う差分がある場合は commit / push せず、理由を報告する。
- 自動化しない処理: 記事本文全文の保存、記事本文全文の転載、原文記事の構成を再現する長文要約、詳細な独自解説ページの自動生成、X 投稿またはメルマガ配信の自動送信。
- 理由: 2026-05-11 時点の副業リポ側 LP は、記事本文の代替になる長文ではなく、日本語タイトル、短い紹介、取得元、公開日、原文リンクを中心にした一覧である。この掲載粒度であれば、LP ファイル更新までを自動化するリスクは比較的小さい。一方で、反映作業を手動に残すと、最新記事の紹介が滞りやすく、運用負荷が自動化の利益を上回る。取得頻度も速報用途ではないため、毎日ではなく 3 日に 1 回程度で十分である。

## D-20260511-015: 日本語タイトル一覧は件数増加に備えて初期表示件数を制限する

- 決定日: 2026-05-11
- 決定: 副業リポ側 LP の日本語タイトル一覧は、公開候補記事が増え続ける前提で設計する。カテゴリごとの初期表示件数を制限し、一定件数を超えたタイトルは折りたたみ、詳細記事一覧またはカテゴリ内の追加表示操作で確認できるようにする。
- 理由: 日本語タイトル一覧は、公開候補記事が増えるほどページ上の占有面積が大きくなる。すべてのタイトルを常時表示すると、ページ冒頭で読者が確認すべき概要、カテゴリ、最新記事への到達が妨げられる。タイトル確認機能は維持しつつ、初期表示の情報量を制御する必要がある。

## D-20260614-016: Codex parallel worktree orchestration は明示依頼時だけ使う

- 決定日: 2026-06-14
- 決定: Codex の既定作業は `main` 上の linear workflow とし、parallel worktree orchestration は利用者が `並列で進めて`、`別で進めて`、`裏で進めて` など同等の意図を明示した場合だけ使う。詳細な運用ルールは root `AGENTS.md` の `Codex Orchestration Modes` を正とする。
- 理由: 通常作業では 1 つの parent thread が task / Goal Bundle を順に調整するほうが、`STATUS.md`、`tasks_backlog.md`、`DECISIONS.md`、spec などの shared / high-conflict files を安全に同期しやすい。parallel worktree orchestration を使う場合も、parent thread が分割、owned files、検証、統合、`main` への Git sync を担い、child thread は専用 worktree / task branch の owned scope と local verify / evidence 報告に留める。parent または repo policy が明示しない限り、child thread は `main` へ push / merge しない。
